# kotlinx.serialization unknown-field case (Kotlin/JVM)

This external library compatibility case checks how an application written with [kotlinx.serialization](https://github.com/Kotlin/kotlinx.serialization) 1.12.0 carries Protobuf fields that its older schema does not know. A small Kotlin adapter runs through ProtoCarry, which decodes each result independently with the newer schema and checks selected fields.

It was written for this repository to exercise ProtoCarry on a Kotlin application path. It is not an external adoption report, and it does not claim a defect in the library. The loss in the first mode is documented default behavior; preserving unknown fields is an opt-in, experimental feature. The loss in the third mode comes from application code.

Kotlin, the JDK and Gradle are needed only for this directory. The ProtoCarry CLI remains a standalone Go binary.

## Prerequisites

- Go 1.27.x and Make, as for the rest of the repository.
- JDK 17. The recorded run used Eclipse Temurin 17.0.21+9. Gradle runs on it and the adapter targets Java 17 bytecode.
- Network access for the first build only. The checked-in Gradle wrapper downloads Gradle 9.2.0 (SHA-256 pinned in `gradle/wrapper/gradle-wrapper.properties`), then Gradle fetches the dependencies declared in [build.gradle.kts](build.gradle.kts). Every downloaded artifact is checked against [gradle/verification-metadata.xml](gradle/verification-metadata.xml).
- macOS or Linux.

No `kotlinc`, `gradle` or `protoc` installation is required.

## Run the case

From the repository root:

```sh
make kotlin-validation
```

This builds `bin/protocarry`, runs the Kotlin unit tests, builds `build/libs/adapter.jar`, then runs the measurement in [validate_test.go](validate_test.go). The runner writes a new `runs/` directory and refuses to reuse one. Move earlier measurements aside before repeating the command.

The individual steps are:

```sh
make build
cd validation/kotlin-serialization
./gradlew --no-daemon test jar
cd ../..
PROTOCARRY_KOTLIN_VALIDATION=1 go test ./validation/kotlin-serialization -count=1 -v
```

Without `PROTOCARRY_KOTLIN_VALIDATION=1` the test is skipped, so `make test` needs neither a JDK nor a built jar.

To run one mode by hand with the same configuration the runner uses:

```sh
mkdir -p evidence
./bin/protocarry check -config validation/kotlin-serialization/no-holder.json -out evidence/kotlin-no-holder
./bin/protocarry check -config validation/kotlin-serialization/preserve-holder.json -out evidence/kotlin-preserve-holder
./bin/protocarry check -config validation/kotlin-serialization/rebuild.json -out evidence/kotlin-rebuild
```

These exit `1`, `0` and `1`. The adapter itself is `java -jar build/libs/adapter.jar MODE`: it reads one unframed binary message on stdin, writes one on stdout and logs on stderr. It reads no external files and does not use the network, so it runs from any working directory.

## Replay offline

The saved cases in [evidence/](evidence/) replay without Gradle and without network access. Only the built jar and a JDK are needed. Run from the repository root:

```sh
./bin/protocarry replay \
  -case validation/kotlin-serialization/evidence/no-holder/s001-baseline \
  -out evidence/kotlin-replay-no-holder \
  -working-dir "$PWD/validation/kotlin-serialization" \
  -adapter '["java","-jar","build/libs/adapter.jar","no-holder"]'
```

This exits `1` with the same assertions as the saved case. Use `preserve-holder` or `rebuild` as the directory and mode to replay the other two; `preserve-holder` exits `0`. The explicit overrides make the bundle usable in any checkout, because saved manifests contain the absolute paths of the recording machine. Output directories must be new.

Every run of the validation also replays all nine cases it just produced and all nine committed cases, and requires the same outcome, exit code and assertions.

## Schema, fixtures and contract

The [old](old.proto) and [new](new.proto) schemas are proto3, with descriptors in `old.pb` and `new.pb` generated by `make fixtures`. The older schema knows `id = 1`, `revision = 2` and a singular `child = 4` with `label = 1`. The newer schema adds `future_note = 3` to the root and `future_note = 2` inside `child`.

The single [seed](seed.bin) is `{id: "A", revision: 7, future_note: "future-root", child: {label: "seed", future_note: "future-child"}}`.

All three modes use the same descriptors, seed and contract:

- Selected added fields: `future_note` (#3) and `child.future_note` (#4/#2).
- Controls known to the older schema: `id`, `revision` and `child.label`.

ProtoCarry creates three cases per mode: the unchanged seed and one with a new value for each added field. Byte-for-byte equality is not required; field order may differ.

## A Kotlin model that keeps unknown fields

The holder is a property of type `ProtoUnknownFieldHolder` with the default `ProtoUnknownFieldHolder.Empty`. It needs no `@ProtoNumber`; the library recognizes it by type and fills it with the raw bytes of fields the model does not declare. See [Models.kt](src/main/kotlin/protocarry/kotlincase/Models.kt).

```kotlin
@file:OptIn(ExperimentalSerializationApi::class)

@Serializable
data class HolderChild(
  @ProtoNumber(1) val label: String = "",
  val unknown: ProtoUnknownFieldHolder = ProtoUnknownFieldHolder.Empty,
)

@Serializable
data class HolderEnvelope(
  @ProtoNumber(1) val id: String = "",
  @ProtoNumber(2) val revision: Int = 0,
  val unknown: ProtoUnknownFieldHolder = ProtoUnknownFieldHolder.Empty,
  @ProtoNumber(4) val child: HolderChild? = null,
)
```

The holder in `HolderEnvelope` is declared before `child` on purpose. The compiler plugin derives a position-based number for a property without `@ProtoNumber` and warns when it collides with an explicit number. Declared last, the root holder would get number 4, the same as `child`. The number is not used for the holder, so only the warning is avoided.

## Why the nested model needs its own holder

Each message is decoded by its own model. Unknown fields found inside `child` are bytes of the nested message, and the root holder never sees them. A holder at the root alone keeps `future_note` (#3) and still drops `child.future_note`. A Kotlin test, `nestedModelNeedsItsOwnHolder`, demonstrates this with a root-only holder model. It is not one of the three ProtoCarry modes. The positive mode declares a holder in both `HolderEnvelope` and `HolderChild`.

## Carrying an object versus rebuilding it

Mode 2 decodes into `HolderEnvelope` and encodes the same object, so the holders written on decode are written back.

Mode 3 decodes into the same holder model, then an application mapper builds a new object from the known properties:

```kotlin
fun HolderEnvelope.rebuildFromKnownProperties(): HolderEnvelope = HolderEnvelope(
    id = id,                                              // copied
    revision = revision,                                  // copied
    child = child?.let { HolderChild(label = it.label) }, // label copied, child holder not copied
)                                                         // root holder not copied: defaults to Empty
```

Known properties are carried over. Both holders fall back to `Empty`, because nothing passes them on. The adapter logs this on stderr: decoded holders hold 13 root and 14 child bytes, rebuilt holders hold 0 and 0. A `copy()` call on a data class would keep the holder; building a fresh instance from selected properties does not.

## Results

Recorded in [results.json](results.json) from a run on macOS arm64, with representative bundles in [evidence/](evidence/). Each mode ran three cases through ProtoCarry 0.1.2 (recorded; later runs replay it with the current version) with no skipped cases and no infrastructure errors.

- **No holder** (`no-holder.json`): FAIL, exit `1`, all three cases. `future_note` (#3) expected `"future-root"`, actual `""`. `child.future_note` (#4/#2) expected `"future-child"`, actual `""`, with the parent present. Controls `id`, `revision` and `child.label` preserved.
- **Holder carried** (`preserve-holder.json`): PASS, exit `0`, all three cases. Both added fields and all three controls preserved. The adapter output is 40 bytes.
- **Rebuilt without holder** (`rebuild.json`): FAIL, exit `1`, all three cases. The same two paths and values as the first mode, with controls preserved. The output is 13 bytes.

Checks beyond the three modes:

- A FAIL comes only from a clean adapter run: exit status `0`, no timeout, and every assertion evaluated. Two control configurations, a missing jar and an unknown mode, give `INFRASTRUCTURE_ERROR` with exit `4` and no PASS or FAIL.
- `./gradlew test` decodes each adapter result again with a new Kotlin model that knows every field. It confirms the same three outcomes, but ProtoCarry's independent Go decoder remains the oracle.
- The adapter reports its runtime on stderr. The recorded run observed JDK 17.0.21+9, Kotlin 2.4.10 (compiler and runtime) and kotlinx-serialization-protobuf 1.12.0, each also resolved by the build. The runner fails if the Kotlin or library version differs.
- On macOS, the two replays above (`no-holder` and `preserve-holder` baselines) were also run once under `sandbox-exec` with network access denied, and gave the same results. CI does not enforce this.

## Versions and references

- kotlinx.serialization 1.12.0 (`kotlinx-serialization-protobuf`), Kotlin 2.4.10 with its serialization compiler plugin, Gradle 9.2.0, JDK 17, ProtoCarry 0.1.2.
- [v1.12.0 release](https://github.com/Kotlin/kotlinx.serialization/releases/tag/v1.12.0), the [documentation for preserving unknown fields](https://github.com/Kotlin/kotlinx.serialization/blob/v1.12.0/docs/formats.md#preserving-unknown-fields-experimental) and [pull request 2860](https://github.com/Kotlin/kotlinx.serialization/pull/2860), which introduced the feature.
- The holder behavior described here was also checked in the 1.12.0 sources jar: the holder is selected by its type, and the API is experimental and requires `@OptIn(ExperimentalSerializationApi::class)`.

## Limits

- The result applies to these descriptors, this seed and contract, this adapter, these versions and one JDK on the tested platforms. It does not cover other schemas, repeated fields, maps, oneofs, enums, proto2, other Kotlin targets or other serialization libraries.
- ProtoCarry reports loss at the adapter's output. The internal stderr diagnostics, not ProtoCarry, point to the rebuild step.
- The holder stores raw bytes and has no API to inspect them. The feature is marked experimental, so its behavior may change in later releases.
- The Gradle dependencies are pinned by hand. Dependabot does not update them, because the versions identify the tested library release.
- Offline replay depends on the jar and a JDK. It does not use Gradle, and the adapter has no network code, but ProtoCarry does not sandbox it.
- Recorded manifests keep absolute paths of the recording machine. Replay with the overrides above.
